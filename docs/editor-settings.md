# Editor settings

Indent, line endings, charset and line width are facts several tools have to agree on. A repository states them once, in the `[editor]` table of the Cinch config, and Cinch writes the root `.editorconfig` from it.

`.editorconfig` cannot extend another file and editors only read it from the repository's own folders. So it cannot follow the preset, generated, root chain the tool configs use. Cinch writes the whole file instead.

## The table

```toml
[editor]
charset = "utf-8"
indent_style = "space"
indent_size = 2
end_of_line = "lf"
final_newline = true
trim_trailing_whitespace = true
line_width = 100

# Facts for some files. A later entry wins over an earlier.
[[editor.overrides]]
files = ["Makefile", "*.mk"]
indent_style = "tab"
```

Every key is optional. Cinch writes only what the table states, and ships no defaults of its own here. Two keys have other names in the file: `final_newline` becomes `insert_final_newline`, and `line_width` becomes `max_line_length`. An override with several globs gets one section for each. An unknown key is an error, as everywhere in the Cinch config.

## Checking files

Set `check = true` in `[editor]` to check selected files that have no active formatter. Pin `editorconfig-checker = "4.0.2"` in `mise.toml` and install that tool through mise. Existing editor configurations opt in explicitly because enforcement requires an additional executable. The first integration supports macOS and Linux. An enabled editor check on another platform is incomplete.

Bun's formatter owns its supported JavaScript, TypeScript, JSON, YAML, TOML, Markdown, CSS, HTML and related extensions while `format.enabled` is true. rumdl owns Markdown while `markdown.enabled` is true. Taplo checks TOML syntax and schemas, so an unformatted TOML file can still receive the editor check. Python, shell, plain text and extensionless files can receive it too, when selected by the repository's include policy. A formatter disabled by a path override leaves that path eligible. Setup files are checked by their setup adapters.

`explain` shows each selected editor check. The pinned engine reads a temporary copy of the file and the same rendered editor settings used for generation, including the ordered editor overrides. Authored root and nested `.editorconfig` files do not override those facts in this isolated check. Setup validation separately reports when the root `.editorconfig` differs from the declared table.

Findings name the editor setting, such as `indent_style` or `final_newline`, and retain the engine's line or line range. Whole-file findings point at line one. Native `editorconfig-checker-disable` comments keep their engine meaning. A required file the engine leaves out, unsupported diagnostics, and a missing or incompatible executable produce an incomplete result. An explicitly selected nested `.editorconfig` cannot validate itself as its own policy and is incomplete.

`check` and `fix` both report these findings without repairing them. A repair remains the owner's edit or its formatter's work. The check creates and removes its temporary input outside the repository.

## Who writes the file

- `cinch doctor --fix` writes `.editorconfig`. `cinch check` and `cinch doctor` report it when it is missing or differs from the table, and the finding says to make the change in `[editor]`.
- `cinch fix` never writes it. Like every file Cinch keeps, a stale one stops `fix` until `cinch doctor --fix` has run.
- The file starts with a "Generated by Cinch" line. A file without that line was written by a person. Cinch overwrites it in one case only: it states exactly what `[editor]` states and holds nothing else, so nothing is lost. Otherwise the finding asks for its settings to be moved into `[editor]` and the file to be deleted, and names what the table cannot hold. After that `cinch doctor --fix` writes the generated one.
- `cinch init` writes it too, when the config that is already there has an `[editor]` table.
- A config that states `[editor]` and also excludes `.editorconfig` is an error, for `doctor` and for `fix`: Cinch cannot keep a file the config leaves out.
- Without an `[editor]` table, `.editorconfig` is not Cinch's. It is left alone and is no part of the setup.

## Starting from a file you already have

`cinch init`, in a repository with no Cinch config and a hand-written `.editorconfig`, reads the file into the `[editor]` table of the config it writes. The `[*]` sections become the base facts, and each other section becomes one `[[editor.overrides]]` entry.

Above the table it writes one `# Not carried over:` line for each thing the table cannot hold:

- a key the table does not know, such as `tab_width`
- a value it does not allow, such as `indent_size = tab` or `max_line_length = off`
- a section whose glob holds `[`, `]`, `#` or `;`
- a `[*]` section below a narrower one, which the generated file could not keep in that place
- anything above the first section other than `root = true`
- what the file takes from a `.editorconfig` in a folder above, when it does not state `root = true`. The file Cinch writes always states it, so add that line first if nothing above should apply
- comments

`init` leaves `.editorconfig` as it is. When nothing was left out, `cinch doctor` reports that the file states what the table states, and `cinch doctor --fix` replaces it with the generated one. When something was left out, the file stays until you delete it.

`init` does this only for a repository with no Cinch config. For one that has a config, see the next section.

## Adopting a file later

A repository that already has a Cinch config and a hand-written `.editorconfig` moves it over in one step:

```sh
cinch preset adopt editor
cinch preset adopt editor --yes
```

The first shows the `[editor]` table it would add to the Cinch config and the generated `.editorconfig` that would replace the file. The second writes both. It reads the file the way `init` does.

- It stops, writes nothing and exits 1 when the file states a setting the table cannot hold, such as `tab_width`. It names each one. Take them out, or keep the file by hand.
- It stops the same way when the file does not state `root = true`, because the generated file does and would cut off the settings of a folder above.
- It stops with exit 2 and writes nothing when the Cinch config excludes `.editorconfig`, since Cinch could not keep the file it would write.
- Comments are not carried over. The move says which lines held them.
- When the Cinch config already has an `[editor]` table that states what the file states, only the file is replaced. When the table states something else, it stops: settle the table by hand.
- `cinch preset eject editor` moves nothing. To keep the file by hand again, delete the `[editor]` table and the first two lines of `.editorconfig`.

## Not yet

- Cinch does not yet write these facts into other tools' configs. It does report a tool's config that states one differently: see [shared facts](shared-facts.md).
- Cinch does not yet hold files to these facts. The checks that will do so read the same table, so there stays one source.
- A key the table does not know, such as `tab_width`, cannot be stated.
