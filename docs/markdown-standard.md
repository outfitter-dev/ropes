# The Markdown standard

Outfitter repositories share one set of Markdown rules. It lives in `packages/cinch/presets/rumdl.toml`, in the format [rumdl](https://rumdl.dev) reads, and ships inside Cinch. A Cinch version is therefore also a version of the standard.

The Markdown profile also checks local destinations and heading anchors with pinned Lychee. [Markdown links](markdown-links.md) describes its scope, offline contract, preview limits and scheduled external URL report.

## How a repository gets it

Cinch keeps three files in the repository. All three are committed. rumdl reads them through `extends`, one after the other, and Cinch never merges them into one.

| Layer | File | Who writes it |
| --- | --- | --- |
| Preset | `.outfitter/configs/presets/rumdl.toml` | Cinch. A copy of the standard as this Cinch ships it |
| Generated | `.outfitter/configs/rumdl.toml` | Cinch, from the `[tools.rumdl]` table in the Cinch config. It extends the preset and holds only what the repository stated |
| Root | `.rumdl.toml` | Cinch, or the repository. It extends the generated file |

Do not edit the first two, because `cinch doctor --fix` rewrites them. A later layer wins over an earlier one, key by key.

`cinch check` reports any of the three when it is missing or not what it should be. `cinch doctor --fix` writes them. `cinch fix` writes none of them, and fixes no Markdown until all three are right. `cinch explain` lists each file with its layer. The files are on disk, so running rumdl by hand, or in an editor, applies the same rules as `cinch check`. `rumdl config` prints every setting with the file it came from.

### The root config, generated or your own

Cinch creates `.rumdl.toml` when there is none. The file is a pointer and nothing else:

```toml
# Generated by Cinch. To change a Markdown rule, set it under `[tools.rumdl]`
# in the Cinch config and run `cinch doctor --fix`. To write this file
# yourself, delete this comment and keep the `extends` line.

extends = ".outfitter/configs/rumdl.toml"
```

While the file starts with that comment, Cinch owns it. A pointer with settings added below it is reported and left as it is. Move the settings to the Cinch config, or delete the comment.

Any other `.rumdl.toml` is the repository's own. Cinch never overwrites it. It must extend the generated file, so the chain is not lost, and `cinch check` reports one that does not, with the line to add. `cinch doctor --fix` adds that line when the file has no `extends` at all. That is the only edit Cinch makes to a file a person wrote. A file that already extends something else is reported and left alone: change the line by hand, or opt out. A repository can keep its own `.rumdl.toml` and still set rules in the Cinch config, and its own file wins where both set the same key.

Cinch will not create `.rumdl.toml` when the repository configures rumdl in `rumdl.toml`, `.config/rumdl.toml` or `pyproject.toml`, because rumdl reads only one of them and the new file would hide those settings. Move them into `.rumdl.toml` first.

A repository set up by an older Cinch has the standard at `.outfitter/configs/rumdl.toml` and a one-line `.rumdl.toml`. `cinch doctor --fix` moves it to the three files. The root file keeps the same `extends` line, so nothing else changes.

## A fenced block that is a fragment

The standard formats fenced TypeScript and JavaScript. A block that does not parse cannot be formatted, and is a finding under `code-block-parse`. Documentation sometimes shows a fragment on purpose: one object member, or a line with `...` in it. Put this comment right above the fence to say so. A blank line between the two is fine, and is what the formatter writes:

````md
<!-- cinch-disable-next-line code-block-parse -->

```ts
retries: 3,
```
````

The comment is Cinch's, not rumdl's. rumdl 0.3.5 has no way to leave one block out of formatting, and its own `rumdl-disable` comments do not stop it. The comment is written the way rumdl writes its own, so it can give way to a native form when rumdl has one. Running rumdl by hand still warns about the block.

Cinch checks that the comment is used correctly:

- Above a block that parses, or anywhere but right above a fence, it does nothing. That is a finding under `ropes/unused-disable`, on the comment's line.
- A comment that starts with `cinch-` and is spelled any other way is a finding under `ropes/unknown-disable`, which names the right spelling. It excuses nothing.
- A comment inside a fenced block is that block's text, as in the example above.

The comment covers `code-block-parse` only. For a rumdl rule, use rumdl's own comments.

## Moving from markdownlint

rumdl reads a markdownlint config when a repository has no rumdl config. The moment `.rumdl.toml` exists it stops, so adopting the standard would drop the repository's own rules without a word. Cinch carries them over instead. When it creates `.rumdl.toml` and finds a markdownlint config, it writes the rules that differ from the standard below the `extends` line. That file has no "Generated by Cinch" comment, so it is the repository's own from then on:

```toml
extends = ".outfitter/configs/rumdl.toml"

# Carried over from .markdownlint.json by Cinch.
# Only what differs from the Markdown standard is here.
[global]
extend-disable = ["MD001"]

[MD007]
indent = 4

# Not carried over from .markdownlint.json:
# - `my-rule` is not a rule the new linter has. It may be a custom rule or a tag.
```

`cinch init` shows this as a diff before anything is written, like every other change it makes.

- Cinch reads the rules the old linter would have used. A `.markdownlint.jsonc`, `.json`, `.yaml` or `.yml` file comes first, in that order, because it replaces the `config` block of a markdownlint-cli2 file beside it. Without one, the rules are the `config` block of `.markdownlint-cli2.jsonc`, `.markdownlint-cli2.yaml` or the `markdownlint-cli2` key in `package.json`. Any file that was not read is named in the notes.
- The translation is rumdl's own (`rumdl import`). Cinch then compares rules by ID, so `no-inline-html` and `MD033` are the same rule, and drops every value the standard already sets and every value rumdl added that the old config did not state. An option rumdl renames, such as `stern` to `strict` on MD013, is carried under its new name. When a rule appears under two names, the last entry counts.
- A rule the old config switched off stays off, under `extend-disable`. A rule the standard switches off that the old config configured or switched on stays on. Then `disable` replaces the standard's list and repeats what stays off. A config with `default: false` becomes an `enable` list of the rules it switched on, and the rules the standard adds are switched off beside it.
- What cannot be carried over is listed in a comment by name: custom rules and tags, `extends`, and markdownlint-cli2 settings such as `customRules`. `globs` and `ignores` choose files, which is the Cinch config's job. When `cinch init` writes the first `cinch.toml`, it puts `ignores` and negated `globs` there as `exclude`, and other `globs` as `include`, unless they only say `**/*.md`. The old linter reads a pattern that names a directory, such as `dist`, as everything under it, so every pattern that does not end in a Markdown extension or `**` is written twice: `dist` and `dist/**`. A pattern a Cinch glob cannot say, such as an absolute path or an extended glob, is named in a comment and not written. The same goes for an `exclude` that would leave out a file Cinch keeps, such as `.outfitter/configs/rumdl.toml`. A `cinch.toml` that is already there is left alone, and the note in `.rumdl.toml` says to add the lines by hand. `gitignore` needs no line: Cinch already leaves out the files git ignores.
- A config that is a script, such as `.markdownlint.cjs`, is never run. Cinch reports it and does not create `.rumdl.toml`. Write the file by hand.
- A `.rumdl.toml` that is already there gets the same rules when `cinch init --yes` adds its `extends` line, and only then. `cinch doctor --fix` adds the line and nothing else, and leaves the old config where it is. What the file already sets stays as it is, and a different value in the old config is named in a comment. A new option goes under the table's own header, and a rule the file does not mention gets a new table at the end. An option Cinch cannot place, because the file writes that rule's settings inline, is named in a comment to add by hand. A file that already extends the standard is not touched, so a rule removed from it later does not come back.
- The translation needs rumdl on `PATH`. Without it the step is incomplete and nothing is written.
- `cinch init --yes` removes the old config files once the new config is written, and the preview names them first. They go only when everything in them was carried over and the setup ended clean. Anything listed as not carried over keeps them in place, and so does a value that an existing `.rumdl.toml` overrides, a script, or file choices that a `cinch.toml` that was already there did not get. The same goes for a rule the old config switches on that the `disable` or `enable` lists in an existing `.rumdl.toml` switch off, and for a `.rumdl.toml` that the Cinch config leaves out of the run, because then nothing was carried into it. `init` prints each reason. A `.rumdl.toml` that extended the standard before the run also keeps them, because Cinch can no longer tell what was carried over. `cinch check` and `cinch fix` never remove them. Cinch does not remove what else names the old linter. `init` lists it under "Still here, and not removed by Cinch", and as `retired.leftovers` with `--json`: `.markdownlintignore`, the `markdownlint-cli2` settings in `package.json`, the packages still installed, the package scripts and `lint-staged` settings that run it, and the hook and workflow files that mention it (lefthook, pre-commit, husky, lint-staged and `.github/workflows`). This list is reported even when no old config file is left, and it never keeps the old config files in place.

`cinch init --yes` and `cinch doctor --fix` write these files. `cinch fix` touches no Markdown until they are right, so the first fix already uses the standard.

## Take a newer standard

Update Cinch, run `cinch doctor --fix`, and review the diff of `.outfitter/configs/presets/rumdl.toml`. Until then `cinch check` fails, so a repository cannot drift from the Cinch it pins without someone seeing it.

## Opt out

```toml
[markdown]
preset = false
```

With that in the Cinch config, Cinch keeps none of the three files and rumdl uses whatever config the repository has.

## Change it for one repository

State the change in the Cinch config, under `[tools.rumdl]`, in rumdl's own words. Cinch copies the table into the generated file as it stands and does not read its keys.

```toml
# cinch.toml
[tools.rumdl.global]
extend-disable = ["MD024"]

[tools.rumdl.MD007]
indent = 4
```

Then run `cinch doctor --fix`. Until then `cinch check` reports the generated file as stale, and `cinch fix` stops. The generated file now reads:

```toml
extends = "presets/rumdl.toml"

[global]
extend-disable = ["MD024"]

[MD007]
indent = 4
```

- A rule's own table merges key by key. Setting `indent` under `MD007` changes only that key.
- `disable` replaces the standard's list. To switch off one more rule and keep the rest, use `extend-disable`.
- The table cannot set `extends`, because Cinch writes that line itself.
- A `[tools.rumdl]` table beside `preset = false` is an error, since nothing would read it. So is a table for a tool Cinch generates no config for.

A repository that already states its rules in `.rumdl.toml` can move them into this table with `cinch preset adopt markdown`, and back with `cinch preset eject markdown`. See [Presets](presets.md).

The settings several tools must agree on, such as indent and line width, are not part of this table yet.

## Testing a rule migration

The Markdown migration parity fixture runs markdownlint and the production rumdl adapter on the same files. It compares findings by relative path, line, and the migration's canonical rule ID, and preserves multiple findings on the same line. A missing engine or unusable output gives an incomplete report.

The frozen workspace install supplies the pinned `markdownlint` engine, and CI runs the fixture with the pinned rumdl on `PATH`. Run it on its own with:

```sh
bun test packages/cinch/tests/markdownlint-parity.test.ts
```

Test authors can reuse `markdownlintParity` with a trusted legacy rules file, the rule catalog from the migration, and an explicit file list. It uses the migration's config reader and the markdownlint engine API, so personal settings and discovery rules cannot change the selection or findings. The fixture compares built-in rules, with custom rules and inherited legacy configs outside its scope.
